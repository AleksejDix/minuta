import { plainDate } from "../../../../components/temporal";
import { divideWith, periodWith } from "@aleksejdix/minuta/core";
import { temporalUnits } from "@aleksejdix/minuta/temporal";
import Timeline from "../../../../components/diagrams/Timeline.astro";

export const weeksOfMarch = (units) =>
  divideWith(
    units,
    periodWith(units, plainDate("2026-03-01"), "month"),
    "week"
  );

minuta does not do date arithmetic itself. A **date engine** (also called an
adapter) does it: a small function that makes **units**. Units are plain data, one rule set per unit of time (year,
quarter, month, week, day, hour, minute, second), plus the week start, the
weekend and the time zone.

You make units once and pass them to `withUnits`, to the `…With` functions
of `@aleksejdix/minuta/core`, or to the plugins.

```ts
import { temporalUnits } from "@aleksejdix/minuta/temporal";
import { withUnits } from "@aleksejdix/minuta/core";

const time = withUnits(temporalUnits({ weekStartsOn: "sunday" }));
time.period(new Date(2026, 2, 18), "week");
// → Sun Mar 15 – Sat Mar 21 2026
```

The default `minuta` entry already uses `temporalUnits()` with weeks starting
on Monday. You need this page when you want another week start or a fixed
time zone.

## The engines

| Function                               | Entry                            | Library to install                                 | Time zone                                  | Pick it when                               |
| -------------------------------------- | -------------------------------- | -------------------------------------------------- | ------------------------------------------ | ------------------------------------------ |
| [`temporalUnits`](../temporal-units/)  | `@aleksejdix/minuta/temporal`    | none (`@js-temporal/polyfill` for Safari, Node 24) | the computer's                             | the default choice.                        |
| [`dateFnsTzUnits`](../temporal-units/) | `@aleksejdix/minuta/date-fns-tz` | `date-fns`, `@date-fns/tz`                         | **any IANA zone you choose** (default UTC) | you need one fixed zone, e.g. on a server. |

`date-fns` and `@date-fns/tz` are optional dependencies of minuta.
`@js-temporal/polyfill` is not; install it where Temporal is missing.

## Same options everywhere

Both engines take the same two options. `dateFnsTzUnits` adds `timeZone`.

| Option         | Default                  | What it does                                                                        |
| -------------- | ------------------------ | ----------------------------------------------------------------------------------- |
| `weekStartsOn` | `"monday"`               | The first day of the week: `"sunday"` … `"saturday"`, or 0 (Sunday) … 6 (Saturday). |
| `weekend`      | `["saturday", "sunday"]` | The days counted as weekend by `isWeekendWith` and `isWeekdayWith`.                 |
| `timeZone`     | `"UTC"`                  | Only `dateFnsTzUnits`: the IANA zone to compute in.                                 |

The week start is never taken from a library's locale. It is Monday unless
you set it.

## Same results

Both engines follow the same contract and are run against the same test
suite, so they give the same periods for the same input. For example, on a
computer in Europe/Zurich, both say (`dateFnsTzUnits` with
`timeZone: "Europe/Zurich"`):

```ts
time.period(new Date(2026, 2, 18), "week"); // → Mon Mar 16 – Sun Mar 22
time.duration(time.period(new Date(2026, 2, 29), "day"), "hour"); // → 23 (clocks go forward)
time.duration(time.period(new Date(2026, 1, 10), "month"), "day"); // → 28
```

The one real difference is the time zone: only `dateFnsTzUnits` computes in
a zone you choose. `temporalUnits` computes in the computer's zone, so the
same code gives other days on a server in UTC than on a laptop in Tokyo.

## What the units contain

Both engines return the same shape:

- a spec for each built-in unit: `year`, `quarter`, `month`, `week`, `day`,
  `hour`, `minute`, `second`;
- `timeZone` — the zone name, e.g. `"Europe/Zurich"`;
- `weekStartsOn` — the week start as a number, e.g. `1`;
- `weekend` — the weekend days as numbers, e.g. `[6, 0]`.

Each spec has four functions: `startOf`, `endOf`, `add` and `diff`. That is
all minuta needs from a date engine. You can write your own spec the same
way, see [Date engines](../../../concepts/date-engines/).

## Engine notes

- **dateFnsTzUnits** defaults to UTC, not to the computer's zone, and an
  unknown zone name gives invalid dates instead of an error.
- **temporalUnits** uses the runtime's `Temporal`. Where there is none,
  `await temporalReady()` first: it loads the polyfill and sets the global.
  It does not use Temporal's time zones.
