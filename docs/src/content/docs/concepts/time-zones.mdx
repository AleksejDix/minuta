minuta works with two kinds of values. A `Temporal.PlainDate` is a day on
the calendar, like Mar 20 2026. It has no time zone. A
`Temporal.ZonedDateTime` is a moment in a zone, like 21:00 on Mar 20 2026 in
Zurich. The same moment is already Mar 21 in Tokyo.

So days, weeks, months and years are plain dates, and need no zone. Hours,
minutes and seconds are moments, and always carry one. This page explains
which zone, and how to choose.

## Dates have no zone

A day made from a `PlainDate` is the same day on every computer:

```ts
import { day } from "@aleksejdix/minuta";

day(Temporal.PlainDate.from("2026-03-20"));
// → { start: 2026-03-20, end: 2026-03-21, unit: "day" }, everywhere
```

A `ZonedDateTime` brings its own zone. Its period is computed in that zone,
whatever the computer's zone is:

```ts
day(Temporal.ZonedDateTime.from("2026-03-21T05:00[Asia/Tokyo]"));
// → { start: 2026-03-21, end: 2026-03-22, unit: "day" }
```

## A moment needs its zone

An `Instant` is an exact moment with no zone, like 20:00 UTC on Mar 20 2026. A `PlainDateTime` is a wall-clock time with no zone. Neither says
which day it is: 20:00 UTC is still Mar 20 in Zurich, but already Mar 21 in
Tokyo.

So minuta does not take them. It never guesses a zone. Give the value one
with Temporal first, and the day follows that zone:

```ts
import { day } from "@aleksejdix/minuta";

const moment = Temporal.Instant.from("2026-03-20T20:00:00Z");

day(moment.toZonedDateTimeISO("Europe/Zurich")).start;
// → 2026-03-20 (21:00 there)
day(moment.toZonedDateTimeISO("Asia/Tokyo")).start;
// → 2026-03-21 (05:00 there)
day(moment.toZonedDateTimeISO("UTC")).start;
// → 2026-03-20
```

A `PlainDateTime` gets its zone the same way:
`Temporal.PlainDateTime.from("2026-03-20T21:00").toZonedDateTime("Europe/Zurich")`.

## The units decide where dates become moments

Sometimes minuta has to turn a date into moments: when it divides a day
into hours, or makes an hour period from a `PlainDate`. Then it uses the
units' `timeZone`. The default `minuta` entry and `createUnits()` use the
zone of the computer the code runs on, so a date's hours can differ from
computer to computer:

```ts
import { hour } from "@aleksejdix/minuta";

hour(Temporal.PlainDate.from("2026-03-20")).start;
// → 2026-03-20T00:00[Europe/Zurich] on a computer in Europe/Zurich
// → 2026-03-20T00:00[Asia/Tokyo] on a computer in Asia/Tokyo
```

In a browser that is usually what you want: users see their own days. On a
server, the computer's zone is often UTC, which is rarely what your users
mean by "today".

## Choosing a zone

Pass an IANA zone name to
[`createUnits`](../../api/minuta/create-units/). Then every function
turns dates into moments in that zone, wherever it runs:

```ts
import { createUnits, withUnits } from "@aleksejdix/minuta";

const tokyo = withUnits(createUnits({ timeZone: "Asia/Tokyo" }));

tokyo.hour(Temporal.PlainDate.from("2026-03-20")).start;
// → 2026-03-20T00:00[Asia/Tokyo], on any computer
```

For a fixed zone everywhere, `createUnits({ timeZone: "UTC" })`. Or pass
`ZonedDateTime`s in the zone you want: their periods keep it.

:::caution
A misspelled zone name is not checked by `createUnits`. It throws a
`RangeError` from Temporal the first time a date becomes a moment.
:::

Everything that turns dates into moments follows the zone of the units, not
the computer's:

- `hour`, `minute`, `second`, and `divide`, `count`, … with those units,
- day grids of a date ([`dayGrid`](../../api/minuta/day-grid/)).

## The `timeZone` setting

All units from `createUnits` carry the zone name:

```ts
import { createUnits } from "@aleksejdix/minuta";

createUnits().timeZone; // → "Europe/Zurich" (on a computer in Zurich)
createUnits({ timeZone: "Asia/Tokyo" }).timeZone; // → "Asia/Tokyo"
```

Periods made from a `ZonedDateTime` do not use it: they stay in their own
zone.

## Showing dates in the right zone

A date period's `start` and `end` are `PlainDate`s. Their fields — `day`,
`month`, `dayOfWeek`, `toString()` — are the same everywhere. A time
period's `ZonedDateTime`s read in their own zone, not the computer's.

- **To display**, use [`toLocaleString`](../../api/minuta/to-locale-string/).
  A moment is shown in its own zone:

  ```ts
  import { hour, toLocaleString } from "@aleksejdix/minuta";

  const tokyoHour = hour(
    Temporal.Instant.from("2026-03-20T20:00:00Z").toZonedDateTimeISO(
      "Asia/Tokyo"
    )
  );

  toLocaleString(tokyoHour, "en-US"); // → "Mar 21, 5:00 AM", on any computer
  ```

- **To compare**, use minuta: `contains(month, day)` or
  `equals(month(a.start), month(b.start))`.

## Clock changes (DST)

Many zones switch to summer time (daylight saving time, DST) once a year and
back once a year. In Europe/Zurich in 2026:

- On **Mar 29** the clocks jump from 02:00 to 03:00. The day has 23 hours.
- On **Oct 25** the clocks go back from 03:00 to 02:00. The day has 25
  hours, and 02:00–02:59 happens twice.

minuta follows the real clock:

```ts
import { count, day } from "@aleksejdix/minuta";

// On a computer in Europe/Zurich
count(day(Temporal.PlainDate.from("2026-03-29")), "hour"); // → 23
count(day(Temporal.PlainDate.from("2026-10-25")), "hour"); // → 25
count(day(Temporal.PlainDate.from("2026-06-01")), "hour"); // → 24
```

The rules behind it:

- **Days, weeks, months and years follow the calendar.** A day is
  one date, however long it is on the clock. Clock changes cannot move it.
- **Hours, minutes and seconds follow real time.** One hour is always 60
  real minutes. On Oct 25 there are two different hour periods that both
  start at 02:00 on the clock, one at +02:00 and one at +01:00.

[`dayGrid`](../../api/minuta/day-grid/) lists the real
hours of a day and tells you which clock hour was skipped (`gapHour`) or
repeated (`ambiguousHour`).

[`next`](../../api/minuta/next/) moves a custom period by its own length:
days for a date period, exact time for a time period. The next period after
24 real hours from Mar 28 00:00 starts on Mar 29 00:00 and ends at 01:00 on
Mar 30.

## Zones with unusual offsets

Zones that are offset by 30 or 45 minutes from UTC, such as Asia/Kolkata or
Asia/Kathmandu, work: hours start at full hours on their clock.

A few zones change their clocks by 30 minutes instead of an hour, such as
Australia/Lord_Howe. On those days one hour is cut in two at the clock
change, so a day has 25 or 24 hour pieces. `gapHour` and `ambiguousHour`
count whole clock hours, so `dayGrid` may not report the half hour that
was skipped or repeated.
