minuta does not do date math itself. It asks a **date engine**: a set of
small rules for each unit of time. minuta computes with
[Temporal](https://tc39.es/proposal-temporal/docs/), or with date-fns when
you need a fixed time zone.

## See the idea

The same code, the same month, two sets of units: one with weeks from
Monday, one with weeks from Sunday. Only the units change, and every week
moves with them:

## Units are rules, as data

For every unit (`"day"`, `"week"`, `"month"` …) minuta needs four answers:

- `startOf(date)` — where does the unit containing `date` start?
- `endOf(date)` — where does it end?
- `add(date, amount)` — what is `amount` units later?
- `diff(from, to)` — how many whole units fit in between?

These four functions are a _unit spec_. A set of specs, one per unit, plus a
few settings, is called **units**. It is a plain object:

```ts
import { createUnits } from "@aleksejdix/minuta/core";

const units = createUnits();

Object.keys(units);
// → ["day", "hour", "minute", "month", "quarter", "second", "week", "year",
//    "timeZone", "weekStartsOn", "weekend"]

units.week.startOf(new Date(2026, 2, 18));
// → Mon Mar 16 2026 00:00:00.000
```

The settings travel with the specs:

| Setting        | What it is                                                           |
| -------------- | -------------------------------------------------------------------- |
| `weekStartsOn` | The first day of the week, as a number: 0 = Sunday … 6 = Saturday.   |
| `weekend`      | The weekend days, as numbers. Saturday and Sunday unless you set it. |
| `timeZone`     | The time zone the specs compute in, e.g. `"Europe/Zurich"`.          |

## Adapters make units

An **adapter** is a function that makes units with your settings. Each lives
in its own entry, so you only load the one you use:

| Engine                      | Adapter                                                 | Import                           |
| --------------------------- | ------------------------------------------------------- | -------------------------------- |
| Temporal                    | [`createUnits`](../../api/minuta-core/create-units/)    | `@aleksejdix/minuta/temporal`    |
| date-fns-tz (any time zone) | [`dateFnsTzUnits`](../../api/minuta-core/create-units/) | `@aleksejdix/minuta/date-fns-tz` |

Every adapter takes `weekStartsOn` and `weekend`. Days are named
(`"sunday"`), and the numbers of `Date#getDay()` (0 = Sunday) work too:

```ts
import { createUnits } from "@aleksejdix/minuta/core";

createUnits({ weekStartsOn: "sunday", weekend: ["friday", "saturday"] });
```

`createUnits` computes in the local time zone of the runtime. `dateFnsTzUnits` takes a `timeZone` and computes in it wherever the
code runs (UTC when you leave it out).

Whatever the adapter, periods are always plain objects with `Date`s in
`start` and `end`. The engine is only used inside the specs.

## `minuta`: ready to use

The main entry, [`minuta`](../../api/minuta/overview/), has the Temporal
units built in, with weeks from Monday. There is nothing to set up:

```ts
import { period } from "@aleksejdix/minuta";

period(new Date(2026, 2, 18), "week");
// → Mon Mar 16 – Sun Mar 22
```

Use it when local time and Monday weeks are what you need.

## `@aleksejdix/minuta/core`: bring your own units

[`@aleksejdix/minuta/core`](../../api/minuta-core/overview/) has the same operations
without units built in. There are two ways to use it.

**Bind once with `withUnits`.** You get an object with every operation, all
using your units. This is the usual way:

```ts
import { createUnits, withUnits } from "@aleksejdix/minuta/core";

const time = withUnits(createUnits({ weekStartsOn: "sunday" }));

time.period(new Date(2026, 2, 18), "week");
// → Sun Mar 15 – Sat Mar 21
```

**Pass the units to each call.** Every unit-aware function has a `…With`
form that takes the units first. Pass only the units you use, and the rest
stay out of your bundle:

```ts
import { createUnits, nextWith, periodWith } from "@aleksejdix/minuta/core";

const { day, month } = createUnits();
const units = { day, month };

nextWith(units, periodWith(units, new Date(2026, 2, 18), "month"));
// → Wed Apr 1 – Thu Apr 30

periodWith(units, new Date(2026, 2, 18), "week");
// RangeError: UNIT_NOT_SUPPORTED: no "week" spec in the units passed (available: day, month). …
```

See [`withUnits`](../../api/minuta-core/with-units/) and
[`periodWith`](../../api/minuta-core/period-with/).

## Another time zone

Swap the adapter; the code stays the same. Here a day is computed in
New York, even on a server in Europe:

```ts
import { withUnits } from "@aleksejdix/minuta/core";
import { dateFnsTzUnits } from "@aleksejdix/minuta/date-fns-tz";

const newYork = withUnits(dateFnsTzUnits({ timeZone: "America/New_York" }));

const day = newYork.period(new Date("2026-03-08T12:00:00Z"), "day");
// → 2026-03-08T05:00:00.000Z – 2026-03-09T03:59:59.999Z

newYork.duration(day, "hour"); // → 23, the clocks go forward in New York that day
```

## Calendar and intervals use the same units

Calendar grids ([`@aleksejdix/minuta/calendar`](../../api/minuta-calendar/overview/)) and interval helpers
([`@aleksejdix/minuta/intervals`](../../api/minuta-intervals/overview/))
bind to the same units, with `calendar(units)` and `intervals(units)`, so
they use the same week start, weekend and time zone as everything else:

```ts
import { calendar } from "@aleksejdix/minuta/calendar";
import { createUnits } from "@aleksejdix/minuta/core";

const grids = calendar(createUnits({ weekStartsOn: "sunday" }));

grids.monthGrid(Temporal.PlainDate.from("2026-03-18")).periods[0].start;
// → 2026-03-01, the grid starts on a Sunday
```

## Your own units

Units are plain data, so you can add one. Give it the four functions and put
it next to an adapter's units:

```ts
import { createUnits, nextWith, periodWith } from "@aleksejdix/minuta/core";

const base = createUnits();
const fortnight = {
  startOf: (date) => base.week.startOf(date),
  endOf: (date) =>
    new Date(base.week.add(base.week.startOf(date), 2).getTime() - 1),
  add: (date, amount) => base.week.add(date, amount * 2),
  diff: (from, to) => Math.trunc(base.week.diff(from, to) / 2),
};

const units = Object.assign({ fortnight }, base);

periodWith(units, new Date(2026, 2, 18), "fortnight");
// → Mon Mar 16 – Sun Mar 29, unit "fortnight"
```

This fortnight starts on the week of the date you pass; a real one would
align to a fixed first week. In TypeScript, also add the name to
`UnitRegistry` so `"fortnight"` is accepted as a unit.

:::note
`diff` must count _complete_ units, rounded toward zero, the same way `add`
steps. The adapters guarantee this; your own units must follow it
too, or `duration` gives wrong counts.
:::

## Keep one set of units

A period does not remember which units made it. Use the same units from
start to finish. Moving a Monday week with Sunday units gives a Sunday week
(see [`nextWith`](../../api/minuta-core/next-with/#use-the-same-units-as-the-period)).
Binding once with `withUnits`, in one module that the rest of the app imports,
is the simplest way to keep them consistent.
